What is real

  • When connected, invoice and payment status come from your local server.
  • The configured server can scan Zcash Testnet using a viewing key you provide.
  • The selective receipt leaves hidden fields out of the copied text.

What is sample or not proven

  • Demo mode uses made-up invoices, only in your browser.
  • A receipt summarizes a server record; it is not a cryptographic proof by itself. Verify the TXID in an explorer.
  • Testnet only, no real funds.

THREAT MODEL

Who can see what

A short, honest map of what each party learns. It covers the current design, where a receipt is a view of the server record and not a signed proof.

Who can see what in a SelectiveProof payment
PartyCan seeCannot see
Merchant serverEvery incoming shielded payment to the merchant address (amounts and memos), because it holds the viewing key.Cannot spend funds. It never needs a spending key or seed phrase.
BuyerTheir own payment, the invoice code and the TXID.Other customers' payments to the same merchant.
Person who gets a receiptThe amount, plus only the fields the buyer ticked.Unticked fields. They are left out of the copied text, not just hidden on screen.
Public chain and explorersThat a shielded transaction exists and when it was mined.Amount, sender, receiver and memo. Looking up a TXID also tells the explorer that someone checked it.
Known limits. The merchant viewing key exposes the full incoming history, so run the server on a machine you control. The amount always stays visible on a receipt. An explorer confirms the transaction exists but cannot confirm it paid this amount, so a receipt here is not a signed proof. Use testnet unless you accept real funds being involved.
